# Как я ускорял ECS в Ikigai Engine и сравнивал её с EnTT и Flecs

Когда я впервые поставил ECS своего движка рядом с EnTT и Flecs, простой проход по 100 000 сущностей занял у Ikigai почти в девять раз больше времени, чем у Flecs.

Запрос делал обычную игровую работу — читал скорость и обновлял позицию. Никакой физики, рендеринга или сложной логики. Именно такой маленький тест позволил увидеть, сколько времени съедает сама организация доступа к компонентам.

В этой статье я хочу показать несколько изменений, которые сильнее всего повлияли на результат. А также сценарий, в котором после всех оптимизаций Ikigai всё ещё почти в семь раз отстаёт от EnTT.

## Что есть в Ikigai ECS

### Два способа хранить компоненты, один `forEach`

При регистрации типа я выбираю, где он живёт. Позиция и скорость обычно нужны вместе, поэтому я храню их в архетипе. Сущности с одним набором архетипных компонентов попадают в одну таблицу, где у каждого типа своя колонка. Добавление архетипного компонента меняет таблицу сущности. Сохраняемые значения переезжают, а освободившуюся строку заполняет последняя строка исходной таблицы.

Редкие данные, вроде здоровья у небольшой группы объектов, можно зарегистрировать как `StorageType::Sparse`. Тогда тип получает свой пул на весь мир. Добавление или снятие такого компонента оставляет архетип сущности прежним. Один и тот же `forEach<Write<Position>, Read<Velocity>>` работает с двумя архетипными колонками, с колонкой и sparse-пулом или с двумя sparse-пулами. Есть и `forEachSparse<T>` для прямого обхода одного пула. `Read<T>` даёт `const T&`, `Write<T>` — `T&`.

У EnTT каждый тип по умолчанию живёт в своём sparse-set хранилище. `view` находит пересечение пулов, а owning group может поддерживать общий порядок компонентов для быстрого прохода. В Flecs обычные компоненты хранятся в колонках таблиц. `Sparse` выносит значения за пределы таблицы, но принадлежность компонента по-прежнему влияет на архетип. `DontFragment` выносит значения в sparse-хранилище и позволяет обойтись без дробления таблиц по наличию компонента. [Хранилища и группы EnTT 3.15.0](https://github.com/skypjack/entt/blob/v3.15.0/docs/md/entity.md#storage) · [Sparse и DontFragment во Flecs 4.1.2](https://github.com/SanderMertens/flecs/blob/v4.1.2/docs/ComponentTraits.md)

### Колонка из чанков

Колонка Ikigai ведёт себя как массив со сквозной нумерацией строк, а память выделяется отдельными чанками. В каждом чанке значения одного типа лежат подряд. Хранилище держит массив указателей на эти блоки. При текущем размере 1024 строка 1023 лежит в конце первого блока, строка 1024 — в начале второго. Чтобы расширить колонку, я добавляю блок. Уже созданные значения остаются по своим адресам при росте. При удалении или смене архетипа сама ECS может переместить компонент, поэтому для долгоживущих ссылок я использую handle.

Это влияет на горячий цикл. При плотном запросе я один раз получаю указатели на текущие блоки `Position` и `Velocity` и работаю по локальному смещению. Для доступа по произвольной строке нужно сначала выбрать чанк, затем обратиться к значению внутри него. Крупный блок уменьшает число переходов между блоками, но оставляет больше свободного места в хвосте маленькой колонки. Текущий размер в `ComponentArray` применяется и к архетипным колонкам, и к sparse-пулам.

EnTT тоже хранит упакованные значения по страницам. Для обычных компонентов в версии 3.15.0 размер по умолчанию — 1024 элемента, а страничная структура индекса по ID настраивается отдельно. У EnTT запрос работает со страницами независимых пулов. В архетипе Ikigai один номер строки адресует соответствующие значения сразу в нескольких колонках. Во Flecs обычная колонка таблицы — один непрерывный массив, к которому запрос получает доступ для текущей таблицы. [Размеры страниц EnTT](https://github.com/skypjack/entt/blob/v3.15.0/src/entt/config/config.h) · [Колонки таблицы Flecs](https://github.com/SanderMertens/flecs/blob/v4.1.2/src/storage/table.h)

### Связи между сущностями

В демо один объект следует за другим. Я описываю это как `follower → Follows → leader`. `RelationManager` хранит список исходящих пар `(тип связи, цель)` для каждой сущности. У одного объекта может быть несколько целей одного типа, а повторное добавление той же пары ничего не меняет. Ребро хранится отдельно от компонентов, поэтому добавление связи сохраняет таблицу и строку сущности.

Если `world` уже создан, а `Follows` объявлен как `struct Follows {};` вне функции, добавить и обойти связь можно так. Это тот же API, который использует демо движка.

```cpp
using namespace IKIGAI::ECS;

auto& components = *world.getComponentManager();
const auto follower = world.createEntity();
const auto leader = world.createEntity();
const auto follows = components.getComponentType<Follows>();
auto& relations = components.getRelationManager();
relations.addRelation(follower, follows, leader);

relations.forEachTarget(follower, follows, [&](Entity target) {
    // Читаем нужные компоненты цели, например Position.
});
```

`forEachTarget` передаёт цели в порядке добавления без промежуточного вектора. В демо я сначала выбираю сущности с позицией и скоростью, затем обхожу их цели и читаю позиции. Уничтожение сущности удаляет её исходящие и входящие связи. Входящие ссылки сейчас ищутся обходом списков, так что стоимость удаления зависит от объёма хранилища связей.

В EnTT я мог бы хранить целевой `entt::entity` в компоненте `Follows` и расширять эту модель списком целей и собственной очисткой. Во Flecs `follower.add<Follows>(leader)` добавляет пару, которую можно использовать прямо в запросе, в том числе с wildcard по цели. Flecs также поддерживает встроенные `ChildOf` и `IsA`, обход связей в запросах и правила очистки. Обычная пара Flecs входит в состав таблицы, а `DontFragment` позволяет хранить такие пары отдельно. У Ikigai цена за отдельное хранилище — явный обход из системы. [Иерархии в EnTT](https://github.com/skypjack/entt/blob/v3.15.0/docs/md/entity.md#hierarchies-and-the-like) · [Пары во Flecs](https://github.com/SanderMertens/flecs/blob/v4.1.2/docs/Relationships.md) · [Правила хранения и очистки во Flecs](https://github.com/SanderMertens/flecs/blob/v4.1.2/docs/ComponentTraits.md)

### Системы и структурные изменения

В Ikigai систему можно оформить классом `System` или зарегистрировать через `world.system<Read<T>, Write<U>>("SystemName")`. У системы есть фазы `Awake`, `Start`, `Update`, `FixedUpdate`, `LateUpdate` и `Destroy`. Планировщик учитывает чтение и запись компонентов и внешних ресурсов, порядок `runBefore` и `runAfter` и приоритеты. Системы без конфликтов могут выполняться в одном пакете задач, если доступна система задач движка. Через `CommandBuffer` можно отложить создание и удаление сущностей, добавление и снятие компонентов. Эти команды применяются после выполнения пакета. Ссылка `PendingEntity` позволяет поставить команды на создаваемую сущность до того, как ей выдан обычный ID.

EnTT предоставляет `organizer`, который строит граф зависимостей, а запуск задач остаётся за приложением. Во Flecs есть собственные фазы и pipelines, отложенные команды и точки синхронизации. Ikigai планирует работу систем целиком, а во Flecs можно также распределить итерацию одной системы между рабочими потоками. Замеры ниже посвящены операциям с данными в одном потоке. [EnTT Organizer](https://github.com/skypjack/entt/blob/v3.15.0/docs/md/entity.md#organizer) · [Системы и pipelines Flecs](https://github.com/SanderMertens/flecs/blob/v4.1.2/docs/Systems.md)

### ID при загрузке, ссылки, singleton и события

- `World::registerEntity` позволяет загрузить сущность с сохранённым ID. `EntityHandle` дополнительно проверяет принадлежность миру и поколение сущности. `ComponentHandle<T>` отслеживает поколение конкретного компонента. Его можно разрешить после переноса компонента в другую строку, а после удаления и повторного добавления прежний handle станет недействительным. EnTT использует версии сущностей и предоставляет snapshot loaders, Flecs тоже проверяет поколения ID. [Сущности и загрузка в EnTT](https://github.com/skypjack/entt/blob/v3.15.0/docs/md/entity.md#snapshot-complete-vs-continuous) · [Сущности Flecs](https://github.com/SanderMertens/flecs/blob/v4.1.2/docs/EntitiesComponents.md)
- В каждом мире могут быть singleton-компоненты, например `GlobalConfig`, и типизированные подписки на добавление и снятие компонентов. EnTT предлагает контекст `registry.ctx()` для общих данных и сигналы жизненного цикла. Во Flecs можно объявить `Singleton` и включать такие данные в запросы, а для событий есть observers. [Контекст и сигналы EnTT](https://github.com/skypjack/entt/blob/v3.15.0/docs/md/entity.md#context-variables) · [Singleton Flecs](https://github.com/SanderMertens/flecs/blob/v4.1.2/docs/ComponentTraits.md#singleton-trait) · [Observers Flecs](https://github.com/SanderMertens/flecs/blob/v4.1.2/docs/ObserversManual.md)

## Как я сравнивал ECS

Для проверки я использовал Ryzen 9 9950X, Windows x64, MSVC 19.38 и Release-сборку. EnTT 3.15.0, Flecs 4.1.2 и Ikigai работали из одного бинарника. Замеры однопоточные, с пятью повторами для основных сравнений и семью для отдельных диагностических серий. В новых сериях чистого sparse-прохода — по девять повторов. Дальше везде указаны медианы времени на одну обработанную сущность или операцию.

Набор сценариев перекликается с `abeimler/ecs_benchmark` — итерация, создание и удаление сущностей, структурные изменения. Мой стенд дополнительно разделяет плотные и смешанные запросы, рост таблиц и разные виды пакетов. Все приведённые числа получены локально. Подготовка миров, проверка результата и очистка вынесены из измеряемого участка. [Референсный стенд](https://github.com/abeimler/ecs_benchmark)

## Плотный проход — от 3,75 до 0,46 нс

Начнём с двух небольших компонентов. В примерах ниже общие типы объявляются вне функции, остальной код выполняется внутри неё.

```cpp
struct Position {
    float x = 0.0f;
    float y = 0.0f;
};

struct Velocity {
    float x = 0.0f;
    float y = 0.0f;
};

struct Marker {
    int value = 0;
};
```

В Ikigai создание сущности и обновление позиции выглядит так. Нужны заголовки `ecsModule/world.h` и `ecsModule/componentManager.h`.

```cpp
using namespace IKIGAI::ECS;

World world { ArchetypeLayout::SharedRows };
auto& components = *world.getComponentManager();
components.registerComponent<Position>();
components.registerComponent<Velocity>();

const auto entity = world.createEntity();
components.addComponent(entity, Position { 0.0f, 0.0f });
components.addComponent(entity, Velocity { 1.0f, -0.5f });

const float dt = 0.25f;
components.forEach<Write<Position>, Read<Velocity>>(
    [&](Entity, Position& position, const Velocity& velocity) {
        position.x += velocity.x * dt;
        position.y += velocity.y * dt;
    });
```

Здесь `Write<Position>` и `Read<Velocity>` явно описывают доступ. Чтобы понять `SharedRows`, представим, что в архетипе с позицией и скоростью три сущности.

| Строка | ID сущности | Колонка `Position` | Колонка `Velocity` |
|---:|---:|---|---|
| 0 | 17 | позиция 17 | скорость 17 |
| 1 | 42 | позиция 42 | скорость 42 |
| 2 | 83 | позиция 83 | скорость 83 |

В исходном `PerColumn` колонки архетипа уже шли в одном порядке, но каждая хранила свою таблицу поиска по ID и свою копию списка сущностей. Чтобы найти данные сущности 42 по ID, каждая колонка могла отдельно получить тот же индекс `1`.

В экспериментальном `SharedRows` я перенёс эту привязку в реестр сущностей. Запись для ID 42 хранит указатель на архетип и номер строки `1`. Этого номера хватает, чтобы обратиться к `Position[1]` и `Velocity[1]`. Сам список ID хранится один раз на архетип, а значения по-прежнему лежат в отдельных колонках.

Если я удалю сущность 42, в строку `1` переедет последняя сущность, 83. Обе колонки переместят её значения из строки `2` в строку `1`, а реестр исправит номер строки у ID 83 один раз. При переходе в другой архетип исходный номер строки точно так же используется для переноса всех сохраняемых колонок. Это убирает повторный поиск номера строки и обновление отдельного индекса в каждой колонке.

Обычный конструктор `World()` использует `PerColumn`. Для `SharedRows` архетипные компоненты должны поддерживать перемещение и уничтожение без исключений.

Для EnTT с заголовком `entt/entity/registry.hpp` тот же сценарий выглядит так.

```cpp
entt::registry registry;
const auto entity = registry.create();
registry.emplace<Position>(entity, Position { 0.0f, 0.0f });
registry.emplace<Velocity>(entity, Velocity { 1.0f, -0.5f });

auto view = registry.view<Position, const Velocity>();
const float dt = 0.25f;
view.each([&](Position& position, const Velocity& velocity) {
    position.x += velocity.x * dt;
    position.y += velocity.y * dt;
});
```

Во Flecs с заголовком `flecs.h` я создаю запрос и затем выполняю проход.

```cpp
flecs::world world;
const auto entity = world.entity();
entity.set(Position { 0.0f, 0.0f });
entity.set(Velocity { 1.0f, -0.5f });

auto query = world.query_builder<Position, const Velocity>()
    .cache_kind(flecs::QueryCacheNone)
    .build();

const float dt = 0.25f;
query.each([&](Position& position, const Velocity& velocity) {
    position.x += velocity.x * dt;
    position.y += velocity.y * dt;
});
```

В бенчмарке `view` EnTT и запрос Flecs создаются до таймера. Ikigai подбирает архетипы внутри каждого `forEach`. У Flecs я также измерял вариант с `QueryCacheAuto`.

Главное изменение в плотном пути Ikigai оказалось связано с внутренним циклом. Указатели на участки колонок выбираются один раз на чанк, а затем цикл обращается к значениям по локальному индексу. Это убирает повторяющуюся работу с адресацией из обработки каждой сущности.

В обоих фрагментах `positions`, `velocities` и `entities` относятся к одному подходящему архетипу. `chunk` возвращает участок колонки, а `updatePosition` — обработчик из примера выше.

**До. Доступ по глобальному номеру строки.**

```cpp
// Упрощённо: column[row] обращается к chunk(row / chunkSize)[row % chunkSize].
for (size_t row = 0; row < entities.size(); ++row) {
    updatePosition(entities[row], positions[row], velocities[row]);
}
```

**После. Доступ по локальному смещению внутри чанка.**

```cpp
size_t firstRow = 0;
for (size_t block = 0; block < positions.chunkCount(); ++block) {
    auto pos = positions.chunk(block);  // Выбираем блок один раз.
    auto vel = velocities.chunk(block);

    for (size_t offset = 0; offset < pos.size(); ++offset) {
        updatePosition(entities[firstRow + offset], pos[offset], vel[offset]);
    }

    firstRow += pos.size();
}
```

Смещение `offset` одинаково для `Position` и `Velocity`, потому что обе колонки хранят строки в одном порядке. `pos.size()` учитывает фактическое число строк, в том числе в неполном последнем чанке.

![Плотный проход по 100 000 сущностей, исходные и итоговые медианы](pulse-charts/iteration.png)

В первой сравнительной матрице Ikigai занимал **3,75 нс на сущность**, в итоговой — **0,46 нс**. Для полного прохода по 100 000 сущностей это примерно 375 и 46 микросекунд.

В итоговом прогоне EnTT с `view` получил 1,53 нс, Flecs без кэша запросов — 0,40 нс. Ikigai оказался примерно в 3,3 раза быстрее измеренного пути EnTT и на 16% медленнее Flecs. Сравнение относится к указанным API и этой небольшой операции. EnTT также предлагает группы, а цена их поддержки требует отдельного сценария.

Числа меньше наносекунды здесь описывают среднюю пропускную способность длинного цикла. Это время полного прохода, делённое на число обработанных сущностей.

## Когда компонент есть только у каждой десятой сущности

Плотный проход хорошо подходит для массовых обновлений. Но в игре есть данные, которые нужны лишь небольшой части объектов.

Чтобы проверить такой случай, я оставил позицию в архетипе, а скорость зарегистрировал в sparse-пуле. В отдельном мире настройка и наполнение выглядят так.

```cpp
using namespace IKIGAI::ECS;

World world { ArchetypeLayout::SharedRows };
auto& components = *world.getComponentManager();
components.registerComponent<Position>();
components.registerComponent<Velocity>(StorageType::Sparse);

for (int index = 0; index < 100000; ++index) {
    const auto entity = world.createEntity();
    components.addComponent(entity, Position {});
    if (index % 10 == 0) {
        components.addComponent(entity, Velocity { 1.0f, -0.5f });
    }
}

components.forEach<Write<Position>, Read<Velocity>>(
    [](Entity, Position& position, const Velocity& velocity) {
        position.x += velocity.x * 0.25f;
        position.y += velocity.y * 0.25f;
    });
```

Сам запрос остаётся таким же. Меняется путь получения кандидатов.

Первоначально смешанный запрос тратил слишком много времени на проверку строк архетипа. Я перевёл обход на наименьший подходящий sparse-пул. При 10% совпадений это даёт 10 000 кандидатов из 100 000 сущностей. Затем оптимизировал поиск архетипной строки по ID и повторное использование страницы реестра.

**До. Каждая строка архетипа проверяет sparse-пул.**

```cpp
for (size_t row = 0; row < positionTable.size(); ++row) {
    const auto entity = positionTable.entities[row];
    if (const auto* velocity = velocityPool.findById(entity)) {
        updatePosition(entity, positionTable.positions[row], *velocity);
    }
}
```

**После. Ведёт sparse-пул, позицию находим через реестр.**

Псевдокод ниже показывает быстрый путь `SharedRows` для двух компонентов и одного подходящего архетипа. Колонка `positions` выбирается заранее, а `velocityChunks` даёт участки значений скорости и соответствующие им участки ID.

```cpp
PageCursor cursor;  // Хранит номер и указатель последней страницы.
auto& positions = positionTable.positions;

for (auto [entities, velocities] : velocityChunks) {
    for (size_t offset = 0; offset < velocities.size(); ++offset) {
        const auto entity = entities[offset];
        const auto pageIndex = pageOf(entity);
        if (cursor.index != pageIndex) {
            cursor.index = pageIndex;
            cursor.page = registry.findPage(pageIndex);
        }

        const auto* record = registry.readRecord(entity, cursor.page);
        if (record && record->archetype == &positionTable) {
            updatePosition(entity, positions[record->row], velocities[offset]);
        }
    }
}
```

`readRecord` читает слот по смещению внутри страницы и при необходимости проверяет компактное хранилище загруженных ID. Если следующий ID попадает на ту же страницу, указатель на неё уже есть. Скорость берётся по локальному смещению, а номер строки позиции — из записи сущности.

![Смешанный запрос Ikigai при 10% и 50% совпадений](pulse-charts/mixed.png)

Между исходной и итоговой сравнительными матрицами время на совпавшую сущность сократилось **с 141,44 до 2,55 нс** при 10% и **с 21,28 до 1,64 нс** при 50%.

Здесь я сравниваю две версии Ikigai с одинаковым смешанным размещением данных. В обычном запросе Flecs оба компонента находятся в архетипах. Это другой путь доступа, поэтому его плотные результаты я показываю на отдельном графике.

## Чистый sparse: почему одного быстрого индекса оказалось мало

После смешанных запросов я проверил вариант, в котором и позиция, и скорость находятся в отдельных sparse-пулах. Для этого достаточно изменить регистрацию типов; сам `forEach` остаётся прежним:

```cpp
components.registerComponent<Position>(StorageType::Sparse);
components.registerComponent<Velocity>(StorageType::Sparse);
```

Эти строки выполняются в новом мире до добавления компонентов. Позиция есть у всех 100 000 сущностей, скорость — у 10%, 50% или 100%. Запрос идёт от меньшего пула и ищет соответствующий компонент во втором. В этой фикстуре все кандидаты меньшего пула совпадают: 10% означает 10 000 обрабатываемых сущностей, а не девять неудачных поисков из десяти.

Сначала поиск строки внутри пула использовал `unordered_map`. Переход к страничному индексу сократил время полного запроса примерно с **10–11 до 3 нс на совпадение**. Но EnTT всё ещё был примерно вдвое быстрее.

Я разделил эксперимент на три пробы: пройти ведущий пул, найти строку второго компонента и найти строку вместе с чтением значения. Оказалось, что сам поиск уже занимает около **0,97 нс**, практически как у EnTT. Продолжать оптимизировать только индекс было бы недостаточно.

Ведущий пул я перевёл на обход чанками: указатель на блок выбирается один раз, внутри блока компоненты читаются по локальному смещению. Выбор ведущего пула тоже вынесен из обработки каждой строки. Самостоятельный обход подешевел примерно с 0,65 до 0,39 нс, а полный запрос — ещё на **35–47%**.

Оставалась адресация второго компонента. Его номер строки уже известен, но надо выбрать блок данных и позицию внутри него. У Ikigai блок содержал 100 элементов. Я увеличил его до 1024: деление и остаток для степени двойки превращаются в сдвиг и маску, а блоков на тот же объём данных становится меньше. Это размер блока значений, а не страницы индекса по ID.

| Доля сущностей со скоростью | Страничный индекс, обход строками | Обход чанками по 100 | Обход чанками по 1024 | EnTT в последней серии |
|---|---:|---:|---:|---:|
| 10% | 3,213 | 2,099 | **1,689** | 1,572 |
| 50% | 3,011 | 1,777 | **1,529** | 1,331 |
| 100% | 3,159 | 1,678 | **1,227** | 1,316 |

Здесь медианы в нс на совпавшую сущность, по девять повторов. Только увеличение чанка сократило время ещё на **14–27%**. Поиск с чтением второго компонента теперь близок к EnTT: при 100% это 1,159 против 1,165 нс в отдельной пробе.

В полном запросе при 10% и 50% я ещё отстаю от EnTT на 7–15%. При 100% медиана Ikigai на 7% ниже, но разброс времени Ikigai в этой серии составляет около 14%. Поэтому этот результат я воспринимаю как близкую производительность, а не доказательство устойчивой победы.

У изменения есть цена: для восьмибайтового компонента первый блок теперь резервирует 8 КиБ вместо 800 байт. Это может быть невыгодно при большом количестве маленьких пулов. Изменён общий размер блока `ComponentArray`, поэтому затронуты и архетипные колонки. Их прежние цифры в статье остаются историческими замерами с блоком на 100; новая серия проверяет именно sparse-проход. Корректность проверена тестами в Debug и Release, включая границы чанков и неполный последний блок.

Для меня главный вывод этого этапа — быстро найти номер строки ещё недостаточно. Важно, что происходит после поиска: сколько адресов нужно вычислить и какую память прочитать. При этом изолированные пробы нельзя просто сложить: полный цикл компилируется и исполняется иначе.

## Почему создание пустой сущности оказалось дорогим

Следующий результат был особенно показательным. Даже создание сущности без компонентов занимало 278 нс, а удаление — 143 нс.

Профилирование отдельных операций привело меня к реестру. Я сократил запись сущности, упростил обработку пустого архетипа, а затем заменил хеш-поиск для обычных последовательных ID индексируемыми страницами.

**Запись сущности.** Раньше каждая запись содержала `shared_ptr` на архетип и встроенную таблицу тегов, даже если тегов у сущности не было. После изменения архетипом владеет менеджер, а запись хранит обычный указатель. Поле тегов стало пустым `unique_ptr`, поэтому при создании сущности таблица тегов больше не конструируется.

```cpp
// До
struct Record {
    Tags tags;
    shared_ptr<Archetype> archetype;
    uint64_t generation;
    size_t row = missing;
};

// После
struct Record {
    Archetype* archetype = nullptr;
    uint64_t generation = 0;
    size_t row = missing;
    unique_ptr<Tags> tags;
};
```

При регистрации пустой сущности я раньше сначала проверял ID через `contains`, затем вставлял запись и каждый раз искал архетип по пустой сигнатуре. Теперь `try_emplace` одновременно проверяет ID и вставляет запись, а указатель на пустой архетип запоминается после первого поиска.

**Удаление пустой сущности.** В псевдокоде обе версии уже нашли запись `it` в реестре.

```cpp
// До
removeFromSparsePools(entity);
removeArchetypeRowIfPresent(it->second);
relations.onEntityDestroyed(entity);
records.erase(entity);

// После
if (it->second.archetype == emptyArchetype && sparsePools.empty()) {
    relations.onEntityDestroyed(entity);
    records.erase(it);
    return;
}
// Для остальных сущностей выполняется общий путь удаления.
```

У пустого архетипа нет колонок, но у его сущностей могут быть sparse-компоненты и связи. Поэтому быстрый путь требует, чтобы в мире не было sparse-пулов, и всё равно вызывает очистку связей. `erase(it)` использует уже найденную запись. На этом этапе реестр ещё был хеш-таблицей. Страничный индекс появился следующим шагом.

![Создание и удаление пустых сущностей на 100 000 операций](pulse-charts/lifecycle.png)

В итоговой матрице обе операции занимают около **7,3 нс**. EnTT тратит 17,3 нс на создание и 21,4 нс на удаление. Flecs — 21,4 и 22,8 нс соответственно.

У страниц обнаружился свой проблемный сценарий — загрузка редких ID с большими промежутками. В моём движке загруженная сущность должна сохранить ID. Создавать ради единичных записей большие участки индекса оказалось дорого.

Поэтому реестр стал гибридным. Плотные последовательности используют страницы, редкие загружаемые записи — компактную таблицу. В отдельной контрольной паре регистрация разреженного ID сократилась примерно с 790 до 34 нс, а объём живой памяти на 1 000 таких записей уменьшился в 142 раза.

Именно такие проверки помогли мне оценивать оптимизацию шире одного удачного теста.

## Добавление компонента — где порядок строк решает многое

У сущности может быть восемь компонентов, а игре нужно добавить девятый сразу группе объектов. Для архетипной ECS это перенос всех сохраняемых колонок.

В Ikigai я начал с кэширования плана перехода и общего индекса строки. Затем вынес резервирование целевой таблицы за пределы цикла вставки. После этого появилась возможность копировать непрерывные диапазоны компонентов блоками и уплотнять источник один раз за пакет.

Ниже минимальный пример с одной сохраняемой колонкой. Нужны также `<vector>` и `<span>`. В измерении с восемью колонками исходная сущность содержит восемь отдельных типов, каждый с полем `int`.

```cpp
using namespace IKIGAI::ECS;

World world { ArchetypeLayout::SharedRows };
auto& components = *world.getComponentManager();
components.registerComponent<Position>();
components.registerComponent<Marker>();
std::vector<Entity> selected;
selected.reserve(100000);

for (int index = 0; index < 100000; ++index) {
    const auto entity = world.createEntity();
    components.addComponent(entity, Position {});
    selected.push_back(entity);
}

components.addArchetypeComponentBatch<Marker>(
    std::span<const Entity>(selected), Marker { 7 });
```

Публичный метод принимает ID существующих сущностей. Для длинного непрерывного диапазона тривиальных компонентов без слушателей добавления он выбирает перенос блоками. Порядок ID, распределение по архетипам и свойства типов влияют на выбранный путь.

В EnTT после подготовки своего списка `selected` я резервирую хранилище нового компонента и вызываю вставку диапазона.

```cpp
auto& storage = registry.storage<Marker>();
storage.reserve(storage.size() + selected.size());
registry.insert<Marker>(
    selected.begin(), selected.end(), Marker { 7 });
```

Во Flecs для списка существующих сущностей с компонентами адаптер измеряет такой цикл.

```cpp
for (const auto entity : selected) {
    entity.set(Marker { 7 });
}
```

Эта деталь влияет на интерпретацию результата. В стенде EnTT выполняет вставку диапазона, Ikigai использует пакетный метод, Flecs — поштучный `set`. Публичный `ecs_bulk_init` Flecs при передаче существующих ID требует пустых сущностей.

![Добавление девятого компонента при восьми сохраняемых колонках](pulse-charts/batches.png)

При переносе всей таблицы из 100 000 строк Ikigai получил **14,2 нс на сущность**, EnTT — **15,3 нс**, Flecs — **122,4 нс**. Результат Ikigai близок к EnTT и заметно лучше выбранного поштучного пути Flecs.

А теперь выбираем каждую десятую строку и перемешиваем список выбранных ID. Исходная таблица всё ещё содержит 100 000 сущностей, но переносим мы 10 000.

Ikigai — **138,8 нс**, EnTT — **20,0 нс**, Flecs — **341,4 нс**.

Преимущество над Flecs в этой фикстуре сохраняется. От EnTT я отстаю почти в семь раз. EnTT добавляет новый компонент в отдельное хранилище, а восемь существующих хранилищ сохраняют свои строки. Ikigai платит за перенос и уплотнение архетипа.

Я отдельно разделил стоимость на планирование, запись в цель и уплотнение источника. Пробовал идти по чанкам цели, чтобы сделать запись последовательной. Планирование действительно подешевело, но чтение исходных колонок стало дороже.

Лучше сработал обход по возрастанию исходных номеров строк с записью на позиции, соответствующие входному пакету. В контрольном прогоне запись сократилась с 92,8 до 76,3 нс на выбранную сущность. Полный инструментированный перенос — со 157,1 до 141,1 нс. Публичный вызов без таймеров фаз дал приведённые выше 138,8 нс.

Этот путь использует дополнительную временную память и сейчас включается для узкого диапазона плотности пакета. Компромисс здесь вполне конкретный — около 403 КиБ индекса и битовой маски в измеренной фикстуре ради более выгодного порядка чтения.

## Сколько стоят связи `Follows`

Для бенчмарка я собрал граф из 16 384 источников, у каждого по четыре цели. Три цели общие, четвёртая своя у каждой группы. Все сущности создаются заранее. Отдельно я измерил добавление связи, обход целей по источникам и уничтожение одной цели с очисткой входящих связей. Для обхода использовал тот же `forEachTarget`, что и в примере, и суммировал ID целей.

| Операция | Ikigai | EnTT | Flecs |
|---|---:|---:|---:|
| Добавить связь, нс | 32,97 | 36,53 | 34,43 |
| Обойти цели, нс на связь | 1,39 | 0,89 | 10,02 |
| Удалить цель с 32 входящими связями, мкс | 106,56 | 20,84 | 4,34 |

Добавление у всех трёх в одном диапазоне. Для обхода EnTT получил компактный компонент с вектором ID, Ikigai ищет список по ID источника, а Flecs проходит пары через `entity.each` для каждого источника. Результат Flecs здесь относится к этому API. У него есть и запросы по парам, которые я в этой серии не измерял. [Отчёт и код адаптеров](RESULTS.md#связи-между-сущностями)

Самое заметное различие оказалось в удалении. При тех же 32 входящих связях, но в графе на 1 024 источника, Ikigai укладывался в **2,95 мкс**. В графе в 16 раз больше время выросло до **106,56 мкс**. Когда я поднял число входящих связей до 512 при том же размере большого графа, медиана осталась около **105 мкс**. `RelationManager` проверяет все списки, чтобы найти ссылки на цель. У адаптера EnTT такой же поиск через упакованный пул компонентов, а Flecs находит нужные таблицы по индексам пар. В этом графе источники одной группы также разделяют один набор пар, поэтому результат зависит от структуры графа.

В начале статьи я написал, что вынес связи из архетипов. Этот замер показывает цену решения. Добавить ребро можно без переноса колонок, а при удалении цели поиск её источников пока оплачивается полным обходом графа.

## Что я вынес из этих замеров

Сильнее всего Ikigai ускорился там, где удалось убрать повторную работу из обработки каждой сущности. Общий индекс строки заменил отдельную адресацию колонок. Обход чанка вынес выбор указателей из внутреннего цикла. Пакетный API позволил один раз подготовить переход и использовать блочное копирование.

При этом оптимизации проявляются по-разному. Плотный проход приблизился к Flecs, а создание и удаление пустых сущностей стали быстрее обоих сравниваемых адаптеров. Непрерывный пакет оказался рядом с EnTT. Чистый sparse-проход после изменения индекса и чанков тоже приблизился к нему, хотя при редком втором компоненте ещё отстаёт. Перемешанные структурные изменения остаются заметной слабой стороной моей реализации.

Для меня это хороший ориентир для развития движка. Дальше интерес представляет то, какие из этих нагрузок действительно преобладают в игровой сцене и сколько времени кадра они занимают.

Какие операции оказываются самыми дорогими в ваших ECS — массовые обновления, смена состава сущностей или работа со связями?
