# План утилитарных контейнеров, строк и идентификаторов

Статус: основной набор реализован 18 октября 2026: Id/IdSequence, allocation domains,
ChunkedVector с фасадом ChunkList, FlatMap, StringPool/Identifier, монотонная арена,
ScratchMemory, миграция shader reflection. API и проверки описаны в
[utility-containers.md](utility-containers.md). Ниже сохранён исходный план от
17 октября. Уточнения: пул имён принадлежит reflection и её копиям; старый ChunkList
не запускается отдельным benchmark baseline; микрозамеры не заменяют профилирование
реальных сцен. Следующим шагом добавлен SmallVector; PMR и остальные классы из
раздела «Что добавить позже» не входят в первый набор.

## Решение

Оставить `std::vector`, `std::string` и стандартные алгоритмы базовыми инструментами.
Добавить небольшой набор классов с явными гарантиями: `FlatMap`, `ChunkedVector`,
`StringPool`, `Identifier`; привести в порядок `Id` и подключение аллокаторов.
Замены в движке проводить по конкретным сценариям, после проверки семантики и замеров.

Причины писать свои классы здесь — управление временем жизни, стабильные адреса,
интернирование и интеграция с памятью движка. Само использование STL не является
дефектом. Аллокатор может убрать часть расходов на выделение памяти, но не меняет
структуру контейнера, его локальность или правила инвалидирования ссылок.

Проект использует C++20 на Windows, Linux, macOS, iOS, Android/Quest и Web.
Не вводить обязательную зависимость от C++23 `std::flat_map` или C++26.
Полную миграцию на EASTL и новую глобальную систему `new/delete` не планировать.

## Что обнаружено в коде

### Id и генерация

`src/engine/utilsModule/idGenerator.h`:

- `Id<T>` уже обеспечивает полезное разделение типов и поддерживает hash/сравнение.
  Это хорошая основа, её стоит сохранить.
- Конструктор принимает `unsigned int`, поле имеет тип `int`, преобразования наружу
  снова возвращают разные целые типы. Представление и допустимый диапазон не заданы
  единым контрактом.
- `CurrentID` — изменяемый статический `int` на тип, без синхронизации. Параллельная
  генерация/восстановление вызывает гонку; signed overflow при `++` и `id + 1`
  недопустим.
- Конструктор `IdGenerator(ID)` меняет глобальный счётчик. Восстановление значения
  и выдача нового ID скрыты в конструкторах объектов.
- Генератор начинает с нуля. При этом `Object::getParentID()` использует ноль как
  отсутствие родителя, а `sceneLoading.cpp` отвергает `descriptor.Id <= 0`.
- `IdGenerator` не обеспечивает уникальность загруженных значений: это отдельная
  обязанность реестра/загрузчика. Копирование ID сущности должно сохранять её
  идентичность; запрещать копирование всех `IdGenerator` вслепую нельзя.

Использования: `ecsModule/entityManager.h`, `world.h`, `componentManager.h`,
`utilsModule/event.h`, файловые подписки, редактор, сцены и prefab-ссылки.
ID объектов сериализуются как `int`; изменение разрядности без миграции формата
небезопасно. ID типов компонентов — другой домен, где ноль нельзя объявить
невалидным автоматически.

### ChunkList

`src/engine/utilsModule/chunkList.h` — каталог `unique_ptr<Node>`, связанный список
узлов и отдельный vector в каждом узле. `reserve(CHUNK_SIZE)` уже сохраняет адреса
элементов при обычном добавлении в конец. Проблема не в отсутствии reserve.

Подтверждённые дефекты и ограничения:

- `Iterator::operator++()` на конце последнего полного чанка присваивает `nullptr`
  в `m_Node`, затем обращается к `m_Node->mData`.
- `insert()` вставляет только внутрь одного чанка: не обновляет `m_Size`, не
  переносит переполнение в следующий чанк и может вызвать реаллокацию. После этого
  формула `index / CHUNK_SIZE` перестаёт соответствовать размещению элементов.
- `at()` проверяет только номер чанка; индекс за концом неполного чанка проходит
  проверку. Отрицательные индексы также не обработаны надёжно.
- `begin() const` возвращает итератор с изменяемым доступом к `T`.
- Нет полноценного move API, `emplace_back`, стандартных iterator traits;
  шаблон `CONT` обещает универсальность, но требует vector-подобный контейнер.
- Категория памяти жёстко задана как `Component`, оболочки узлов выделяются через
  `make_unique`; копирующее присваивание не обеспечивает транзакционную замену.

Контейнер используется в обоих `coreModule/ecs/componentArray.h` и
`ecsModule/componentArray.h`. Активный ECS при удалении перемещает последний
компонент на освободившееся место и обновляет `ControlBlock::mPtr`.
Стабильность адресов при росте не означает стабильность адреса компонента при
удалении другого компонента или переходе между archetype.

В `utils/tests/memory/memoryTests.cpp` уже есть проверка `ChunkList` на 350
элементах, но она проверяет индексирование/копирование, а не граничный обход.

### Память и строки

`src/engine/utilsModule/memory/` уже содержит `HeapAllocator`, `LinearAllocator`,
`StackAllocator`, `PoolAllocator`, `FreeListAllocator`, `ObjectPool<T>`,
`SynchronizedAllocator`, профилирование и `StlAllocator<T, Category>`.
Имеются отдельные memory-тесты и конфигурации tracking ON/OFF.

Недостаёт удобного выбора конкретного allocation domain для экземпляра
контейнера: `StlAllocator` сейчас получает общий синхронизированный буфер категории,
а конструктора с переданным аллокатором нет. Профилирующая обёртка не предоставляет
reset/rewind для арен. Это важнее добавления ещё одного общего free-list/pool.

Отдельного общего пула интернированных строк в просмотренном engine-коде не найдено.
Строковые ключи присутствуют в событиях, reflection, ресурсных кешах, материалах,
анимациях. Первый удобный кандидат для `FlatMap` — `ShaderReflection::mNameToUniforms`:
`map<string, size_t>`, заполняемый при reflection и читаемый далее. Это кандидат,
а не подтверждённое узкое место.

## Предлагаемые контракты

### 1. Id и IdGenerator

Сохранить разделение типов `Id<Tag>`. Использовать явное беззнаковое представление
фиксированной ширины (`uint32_t` по умолчанию), `value()`, `valid()`, `invalid()`,
`constexpr` сравнение и `noexcept` hash. Новое невалидное значение — максимальное
значение representation; значение ноль разрешено в доменах, где оно уже значимо.
Предусмотреть extension point для другого representation, без перевода всех ID
движка на 64 бита в первом этапе.

Отделить сервис выдачи значений от хранения значения: `IdSequence<Tag>` с операциями
`next()` и `observeLoaded(id)`. Старый `IdGenerator<T>` временно оставить фасадом
для текущих `Entity`, `World`, событий и подписок.

- Для entity-домена выдавать значения от 1; для component-type сохранить 0.
- На первом этапе entity ограничить положительным диапазоном текущего `int` в
  формате сцен. На границах загрузки проверять диапазон и дубликаты.
- При исчерпании выдавать явную ошибку, без wraparound; `next()` перестаёт быть
  безусловно `noexcept`. Конкурентные `next/observeLoaded` реализовать одной
  проверяемой атомарной CAS-схемой, без переполнения промежуточных выражений.
- `observeLoaded` двигает верхнюю границу выдачи и не доказывает уникальность ID.
  Проверка дубликатов остаётся у владельца сущностей/документа.
- Старые преобразования к `int` временно сохранить для проверенного диапазона,
  места использования постепенно перевести на `value()`/проверяемые адаптеры.
- Существующие корректные числовые ID в сценах и prefab-ссылках сохраняются.
  Новая выдача не должна менять номера загруженных объектов.

`Identifier` не должен наследовать генератор уникальных объектов: два объекта
различаются ID, а одинаковые имена должны получать одинаковый string identifier.
Generation/index handles и сохранённые UUID — самостоятельные типы при появлении
соответствующей потребности, не дополнительные режимы одного `Id`.

### 2. ChunkedVector<T, ChunkSize, Allocator>

Реализовать общий контейнер в `utilsModule/containers/chunkedVector.h`.
Каталог указателей может реаллоцироваться; сами блоки с `T` не перемещаются.
Размер блока фиксирован для экземпляра, по умолчанию выбрать после замеров;
шаблонный параметр позволяет сохранить существующее значение 100 в ECS.

Рекомендуемое хранение: allocator-aware блоки сырой памяти на `ChunkSize` элементов
и каталог блоков. Конструировать только живые `T` через `allocator_traits`,
корректно учитывать over-alignment, время жизни и частично построенные блоки.
Не требовать default-конструктора `T`; поддержать move-only и emplace для
неперемещаемых типов. Не применять `memcpy` к произвольному `T`.

Минимальный API: `emplace_back`, обе формы `push_back`, `pop_back`, `back`,
`operator[]`, `at`, `size`, `empty`, `capacity`, `reserve`, `clear`, `release`,
const/non-const random-access итераторы и доступ к отдельным заполненным чанкам
как `span<T>`/`span<const T>`. Общего `data()` и contiguous-iterator контракта нет.

Гарантии:

- `push_back/emplace_back/reserve` не меняют адреса существующих `T`.
- Итератор хранит владельца и индекс, а не адрес элемента каталога; добавление
  сохраняет итераторы существующих элементов, прежний `end()` инвалидируется.
- `pop_back` уничтожает последний `T`; `clear` уничтожает все живые `T`, сохраняя
  выделенные блоки для повторного использования. `release` освобождает память
  и допустим только при пустом контейнере.
- Перемещение контейнера инвалидирует его итераторы; перенос хранения при равных
  аллокаторах может сохранять адреса элементов. При несовместимых аллокаторах
  перенос требует перемещения `T` и другого контракта; не обещать общий `noexcept`.
- Ошибка выделения/конструирования не разрушает уже существующие элементы и
  сохраняет корректный размер. Копирование доступно только для копируемых `T`.
- Произвольные `insert/erase` не входят в базовый API. ECS выполняет свой явный
  move-last-and-pop; его перемещения и обновление weak-ссылок остаются видимыми.
- Контейнер сам не синхронизирован. Мутации во время параллельного обхода запрещены
  без внешнего протокола.

`ChunkList` временно сделать совместимой обёрткой и мигрировать оба ComponentArray.
Проверить существующие обращения к `moveFrom/moveTo/insert` перед удалением фасада.
Для гарантии неподвижности переживших удаление объектов потребуется отдельный
slot-storage со свободными ячейками; это не обещание данного контейнера.

Для сравнения обязательно включить `std::deque`: он уже сохраняет ссылки при
добавлении в конец. Собственный контейнер оправдывают контроль размера чанков,
переиспользование блоков, chunk-span API и интеграция с allocation domain.

### 3. FlatMap<Key, Value, Compare, Allocator>

Под `FlatMap` в этом плане понимается **упорядоченный массив пар**, не хеш-таблица.
`FlatHashMap` — отдельное имя и отдельный возможный этап.

Начальная реализация: один `std::vector<pair<Key, Value>, Allocator>`, сортировка
по ключу и `lower_bound`. Поиск O(log N), вставка/удаление O(N). Для небольших
или редко меняющихся таблиц это разумный обмен затратами; результат проверяется
измерениями. SoA с отдельными массивами ключей/значений отложить до профилирования.

API: `find/contains/at`, `try_emplace`, `insert_or_assign`, `erase`, `reserve`,
`size/empty/clear`, обход по ключу, пакетное построение через sort+deduplicate.
Для bulk-build задать однозначное правило дубликатов — ошибка по умолчанию;
явные keep-first/keep-last политики могут добавляться при необходимости.
Поддержать transparent comparator и поиск по `string_view` без временной строки.

Запретить изменение ключей через публичный mutable iterator: прокси-ссылка
должна давать `const Key&` и `Value&`, либо API должен предоставлять равноценный
безопасный доступ. Сырой изменяемый vector наружу не выдавать.
Документировать инвалидирование: модификации могут двигать элементы; reserve
не защищает от сдвигов при вставке в середину. После ошибки сортировка и
уникальность ключей должны сохраняться: для in-place сдвигов требовать подходящие
`noexcept` move-операции, иначе строить новый буфер с копированием и commit.
Для move-only типов с бросающим перемещением ограничить соответствующие операции
на этапе компиляции; не оставлять контейнер с повреждённым порядком ключей.

Не подменять им большие часто меняющиеся resource/event/ECS-таблицы автоматически.
Не переводить `Event::mCallbacks` без отдельного решения о подписках/отписках из
выполняемого callback: текущие правила реентерабельности требуют анализа.

### 4. StringPool и Identifier

`StringPool` интернирует строки: копирует уникальные байты в собственные
неперемещаемые страницы и возвращает `Identifier`. `find(string_view)` не вставляет
строку; `intern(string_view)` вставляет при отсутствии; `view(id)` возвращает
стабильный `string_view`. Базовые операции принимают length, а не требуют `strlen`.

Хранение: растущая монотонная арена байтов и индекс `string_view -> entry ID`.
Для первого рабочего варианта использовать `std::unordered_map` с transparent
hash/equality и нашим аллокатором. Записи/метаданные тоже размещать в выбранном
домене. Индекс должен сравнивать байты при совпадении хешей; хеш не является ID.
`FlatMap` с O(N) вставками не использовать как индекс постоянно растущего пула.

Предлагаемый `Identifier` — два 32-битных поля: token пула и типизированный
`Id<StringEntryTag>`. Это даёт 8 байт, безопасное сравнение разных пулов и
возможность локальных пулов для тестов/инструментов. Token выдаётся без повторного
использования, исчерпание проверяется. Разрешение выполняет пул с проверкой token;
`Identifier` не хранит владеющий указатель и не продлевает жизнь пула.

Если замеры докажут необходимость 4-байтного индекса, вводить отдельный локальный
`StringId` с явно ограниченной областью сравнения. Не терять проверку домена
молча ради уменьшения структуры.

Контракты:

- Одинаковые байты в одном пуле дают одинаковый `Identifier`; коллизии хеша не
  объединяют разные строки. В разных пулах identifiers различаются.
- Сравнение case-sensitive, по байтам; UTF-8 хранится без Unicode-нормализации.
  Пустая строка — валидная запись, отдельно от invalid identifier. Embedded NUL
  сохраняется благодаря length; C-string интерфейсы имеют собственное ограничение.
- В конец хранения можно добавлять нулевой терминатор для совместимости, но длина
  и равенство определяются исходными байтами.
- В первой версии нет удаления отдельных строк, refcount и публичного `reset`.
  Все view действительны до уничтожения пула. Пул не копируется и не перемещается;
  при интернировании из собственного view источник остаётся валидным.
- По умолчанию engine-пул живёт дольше его потребителей; владение явное в core,
  порядок shutdown задаётся явно. Динамический пользовательский текст в него не
  интернируется без ограничения: строки живут до завершения domain.
- Сам базовый пул использует внешнюю синхронизацию; engine-фасад обеспечивает
  синхронизацию `intern/find/view`, включая чтение каталога записей. Выданные view
  читаются без блокировки, поскольку байты неизменны и не освобождаются.
- Не публиковать неполную запись при ошибке аллокации; уже выданные ID/view остаются
  валидными. Потерянное место в монотонной арене учитывать, если rollback отсутствует.
- ID зависит от порядка интернирования и процесса: в JSON/сеть сохраняется строка,
  при чтении она интернируется заново. Для воспроизводимого порядка сортировать
  исходные строки, а не числовые значения `Identifier`.

Первый потребитель — lookup таблица имён shader reflection/material. Внешний
строковый API оставить адаптером, горячему внутреннему пути дать перегрузку с
готовым `Identifier`. Интернирование в каждом draw-call не устраняет стоимость
хеширования исходной строки. События и resource keys — следующие отдельные миграции;
пути ресурсов сначала проходят существующую канонизацию, не нормализуются пулом.

### 5. Расширение аллокаторов

**Необходимое в первом наборе:**

1. Конструктор `StlAllocator` с явно переданным владеющим allocation domain,
   сохранение domain при copy/rebind/move. Общий category allocator остаётся
   вариантом по умолчанию. Для невладеющего режима нужен явно выраженный контракт
   времени жизни; не смешивать его неявно с owning handle.
2. Формализовать equality, copy selection, move/copy/swap propagation.
   `swap` при разных доменах должен иметь безопасно определённую политику.
   Проверить освобождение каждым доменом только своих блоков.
3. Растущая страничная монотонная арена с передаваемым upstream allocator,
   лимитом/budget, `used/reserved/peak`, корректным alignment. Существующий
   фиксированный `LinearAllocator` сохранить для ограниченного scratch.
4. Изолированный owner для scoped/frame scratch с явным reset после уничтожения
   потребителей. Начально один домен на поток/задачу, без глобальной блокировки.
   Для нескольких кадров в полёте — отдельные домены и reset только после
   завершения использующих их задач; GPU lifetime учитывать у владельца.
5. Для reset/release обеспечить согласованное снятие записей профайлера. Через
   текущий `ProfiledAllocator` массовый reset сейчас провести нельзя.

Все буферы новых контейнеров, каталоги блоков и string metadata должны использовать
выбранный allocator. Добавить подходящие категории `Container`/`String` при
необходимости, обновив отображение категорий в профайлере.

**Второй этап по потребности:** адаптер `IAllocator -> std::pmr::memory_resource`.
Он полезен для стандартных `pmr` контейнеров и библиотечных API, но не требует
параллельно переводить весь движок на PMR. Реализовать forwarding alignment/bytes,
identity-based equality и явное владение upstream. `StackAllocator` не подключать
к произвольным контейнерам: их порядок освобождения не обязан быть LIFO.
Для PMR допускать только политики с подходящим контрактом deallocation.

TLSF, buddy, собственный общий malloc, lock-free allocator и новый GPU allocator
в этот план не входят: в просмотренных сценариях необходимость не подтверждена.
Нынешний синхронизированный free-list также не объявлять быстрее системного heap
без измерений; линейные поиски и блокировки могут изменить результат.

## Очерёдность работ

| Этап | Результат | Условие завершения |
| --- | --- | --- |
| 0 | Контракты, baseline, отдельный C++20 utility test/benchmark target | Зафиксированы workloads, правила ID/адресов и сборка без renderer/editor |
| 1 | Исправленный Id + проверяемая выдача + legacy facade | Нет нулевых новых Entity, overflow/гонок в выдаче; сцены сохраняют ID |
| 2 | Передаваемый allocation domain и allocator traits | Rebind/copy/move/swap и alignment проходят проверки ON/OFF |
| 3 | ChunkedVector и совместимость ChunkList | Границы чанков, lifetime, итераторы и ECS weak-ссылки проверены |
| 4 | FlatMap и bulk-build | Сравнение с эталонной map, immutable keys, измерения lookup/build |
| 5 | Растущая арена, StringPool, Identifier | Стабильность view, коллизии, домены и shutdown проверены |
| 6 | Одна миграция shader name lookup + измерения | Совпадают результаты reflection/material; есть сравнимые показатели |
| 7 | Выбор следующих миграций и необязательных классов | Решение принято по реальным частотам операций и расходу памяти |

FlatMap и ChunkedVector независимы после allocator foundation; StringPool не должен
зависеть от будущего FlatHashMap. Не блокировать полезные контейнеры разработкой
полной собственной STL.

## Проверки и измерения

Отдельный `utils/tests/containers` с CTest и переключателем интеграции в engine CMake.
Переиспользовать существующие memory-тесты, не подменять их новыми копиями.

- `Id`: типобезопасность, hash, invalid, стартовые значения разных доменов,
  граничный диапазон, параллельная выдача/observe, сохранение/загрузка scene IDs,
  дубликаты, prefab remap, editor undo/redo.
- `ChunkedVector`: размеры 0/1/C-1/C/C+1/2C, полный обход и const-обход, адреса
  при росте каталога, destructor counts, over-aligned/неперемещаемые/move-only T,
  throwing constructor и отказ аллокатора, reuse после clear, move/copy между
  доменами. Отдельно remove-last и remove-middle ECS с обновлением weak-ссылок.
- `FlatMap`: случайные последовательности операций относительно `std::map`,
  пользовательский/transparent comparator, порядок, дубликаты bulk-build,
  неизменяемые ключи, move-only Value и исключения при перемещении.
- `StringPool`: повторные вставки, пустые/длинные/UTF-8/NUL строки, временный
  исходный буфер, намеренно одинаковые хеши, рост страниц и индекса, чужой token,
  отказ аллокации, concurrent engine facade и завершение жизни пула.
- Аллокаторы: баланс байтов/блоков и принадлежность domain, limits, alignment,
  tracking ON/OFF, reset/release и отсутствие устаревших profiler records.

Benchmark проводить в Release без memory tracking; расходы tracking измерять
отдельно. Наборы: 8/32/128/1024 и крупные таблицы, реальные имена uniforms,
повторяющиеся/уникальные строки, hit/miss lookup, bulk-build, insert/erase churn,
покадровый обход/рост ECS. Измерять время, число allocations, used/reserved/peak,
выбросы задержки роста и влияние в реальной сцене. Не устанавливать заранее
универсальное требование «быстрее в N раз».

Сравнения: `FlatMap` с `std::map` и `std::unordered_map`; `ChunkedVector` со старым
`ChunkList`, `std::deque` и `std::vector` с заранее заданным reserve; арены с текущим
free-list и heap. Повторное чтение чанков не должно сравниваться только с ростом
vector без reserve. Результат может обосновать сохранение стандартного контейнера.

Доступные на текущей машине проверки выполнить на MSVC Debug/Release; отдельно
проверять Clang/GCC, Android и Web при наличии соответствующих toolchains.
Непроверенные платформы отмечать явно. Для memory safety использовать доступные
sanitizers; concurrent контракты проверять отдельно там, где поддержан TSan.

## Основания для выбора

- [Boost.Container: flat containers и другие варианты хранения](https://www.boost.org/doc/libs/latest/doc/html/container/non_standard_containers.html)
  — sorted storage, линейные изменения, small/static vector.
- [Abseil: containers](https://abseil.io/docs/cpp/guides/container)
  — отдельный класс flat hash tables, heterogeneous lookup и инвалидирование
  pointers/references при rehash.
- [Проект стандарта: deque.modifiers](https://eel.is/c++draft/deque.modifiers)
  — ссылки на элементы при добавлении в конец и отличающийся контракт итераторов.
- [Проект стандарта: memory resources](https://eel.is/c++draft/mem.res)
  — стандартный адаптерный интерфейс ресурсов памяти.

Это источники контрактов и компромиссов, а не результаты замеров IkigaiEngine.
Существующий локальный graphify-граф использован для навигации к ComponentArray;
выводы о дефектах и текущих API проверены непосредственно в исходниках рабочего
дерева. Удалённый graphify workspace для данной сессии не выбран.
